# 02 — Prove the privileged-helper authorization boundary

**What to build:** Define and prototype the one-shot elevated helper, authenticated local IPC, authoritative plan confirmation, and terminal lifecycle so a future unelevated dashboard cannot become a confused deputy or general administration channel.

**Blocked by:** 01 — Publish the threat model and operation matrix.

**Status:** ready-for-agent

- [x] The strict versioned protocol defines bounded typed requests/results, unknown-field rejection, operation/revision/nonce binding, timeouts, cancellation, redaction, and one terminal response.
- [x] The first-instance remote-client-rejecting pipe design includes its exact DACL and peer PID, token, user, session, integrity/elevation, process lifetime, protected image path, version, hash, and Authenticode checks.
- [x] The dashboard creates the pipe before launching the helper, both peers authenticate before request transmission, and pipe squatting or unverifiable identity fails closed.
- [x] The helper re-observes state, compares the authoritative plan digest, and owns a TaskDialog-style Apply decision bound to one helper instance, user/session, operation, nonce, digest, two-minute monotonic lifetime, and one consumption.
- [x] UAC elevation and dashboard-only consent are explicitly insufficient authorization.
- [x] Positive prototype behavior completes exactly one locally authorized request; negative cases cover remote clients, squatters, wrong user/session/integrity/process/image/hash/signer, dead-peer races, replay, unknown/oversized messages, stale revision, changed plan, timeout, expired consent, second Apply, crash, and secret-response cardinality.
- [x] Unsigned development behavior is possible only behind a disposable-VM guard; production authorization requires an administrator-protected installed path and trusted signer, so later milestones cannot treat a build-directory helper as production-ready before v0.8 packaging/signing.
- [x] The prototype is isolated from production composition, creates no service/scheduler/listener/general shell, and performs no system mutation.
- [x] Security state-machine and feasibility tests are written test-first and pass with redaction/secret scans.
- [x] Both review axes pass with every Critical and Important finding resolved.
- [x] The ticket and authoritative roadmap contain exact verification evidence, and the coherent checkpoint is committed and pushed with unrelated work preserved.
