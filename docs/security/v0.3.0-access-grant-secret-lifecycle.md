# v0.3.0 access-grant and display-once secret lifecycle

Status: design contract only. This document authorizes no production, Windows, network, account, credential, clipboard, or QR mutation.

This contract applies the exact helper authorization binding from OP-02, the protected non-secret ledger/recovery boundary from OP-03/04/23/24/39, the product-group resource proof from OP-06/07/08, and the one selected endpoint binding from OP-28/29. A grant ID, account SID, product-group SID, credential revision, helper operation ID, initiating user/session, pipe instance, and nonce are opaque bindings; none is a secret or reusable authority.

## Grant and transfer state

| Action/state | Required result | Recovery boundary |
| --- | --- | --- |
| Create (OP-12) | Create one opaque non-administrator local account, unable to change its password, in only the product access group. Observe expiry, lockout, and network-logon policy; do not rewrite it. Generate at least 32 cryptographically random bytes for one explicit owner action and make one policy attempt. The account is Disabled pending transfer. | Reject policy failure without reuse or automatic retry. A later explicit Retry is a new action and fresh value. |
| Rotate (OP-14) | Disable the exact proven account, generate one fresh value, advance the revision once, and leave it Disabled pending transfer. | Password rollback/retrieval is prohibited. A post-change failure is Repair needed; rotate again or revoke. |
| Transfer (OP-17/18) | The helper returns one minimum bearer setup code over the initiating-user, session, pipe, nonce, operation, grant, and revision-bound response. The view is dedicated, warned, transient, and cannot activate a grant. | Lost, hidden, timed-out, crashed, unread, malformed, or failed transfer destroys the available copy and leaves the grant Disabled. It may be reissued only by fresh rotation or revoked. |
| Activate (OP-13) | A separate fresh authoritative helper authorization, opaque to public callers and issued only at the helper/friend-test seam, is one-use and bound to operation ID, grant ID, and current displayed credential revision; it enables only the exact Disabled grant. | Absent, mismatched, or reused authorization refuses. Revision mismatch, ambiguity, drift, or uncertain enablement refuses or disables the exact grant. No transfer event activates it. |
| Revoke/delete (OP-15) | Remove only the selected grant from the product group and disable it before optional exact-account deletion; retain the non-secret tombstone. | Do not re-add membership, restore old access, touch shared ACLs, or clean a client remotely. |
| Session closure (OP-16) | Close only separately confirmed, currently attributable session IDs for the exact grant SID and managed share. | Never use a wildcard or all-session action. Sessions are not restored. |

## Minimum setup code and disclosure surfaces

The setup code is live bearer material until host rotation or revocation; hiding it is not expiry and it does not establish physical-device trust. Its only fields are schema version, opaque product-host ID and label, exactly one selected endpoint, share name, helper-observed qualified host-local SAM account, password, credential revision, and generation time. It contains no alternate endpoint, SID, ledger record, diagnostics, folder data, or Tailscale credential.

Password and setup-code data never enter arguments, environment variables, stdout/stderr, logs, audit, diagnostics, ordinary configuration, ledger, crash attachments, or artifacts. Create and rotate obtain their 32-byte values from the internal CSPRNG seam; no caller supplies bytes. Buffers are created late and cleared when the runtime permits. A one-read response atomically consumes the exact binding and setup-code grant/revision pair, so concurrent readers have one winner only. The only disclosure surfaces are that response and its owner-controlled transient view. Clipboard Copy and QR each require an explicit warning. QR is memory-only. Clipboard cleanup compares the exact current value against the value Balls Server wrote and clears only an unchanged match; it never enumerates history or erases newer user content.
