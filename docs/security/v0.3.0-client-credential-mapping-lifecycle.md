# v0.3.0 client credential, mapping, and verification lifecycle

Status: isolated design and prototype evidence for Ticket 07. This contract authorizes no SMB, Credential Manager, drive, filesystem, or Windows mutation.

## Exact client boundary

A setup code contains one exact endpoint only. The endpoint is `(product host ID, grant ID, credential revision, server name, share name, host-qualified SAM account)`. The server name must be a host name: wildcards, UNC roots, aliases, and IP addresses are refused, and the share name must equal the fixed exact value `Balls`. Mapping UNC is exactly `\\server\Balls`; the provider credential target is separately and exactly `server`. The local SAM authority is supplied by the host-observed qualified account and is never derived from either target.

An endpoint update is a separate owner-transferred schema. Import is explicit and is accepted only when its host ID, grant ID, and credential revision equal the existing current-user record. A refused update preserves the selected endpoint, saved target, and mapping intent. There is no discovery, pairing service, alternate setup-code endpoint, alias, IP, automatic switch, or fallback.

## One-action plan

Each explicit Check, Connect, Reconnect, or Switch starts with endpoint, mapping, owner-selected drive-letter, and credential collision observations. Observation failure, unavailable path, used letter, existing mapping, open file, different credential, and unmanaged credential target stop before authentication. A successful action performs exactly one exact-endpoint authentication attempt. It has no retry, alias, IP, alternate path, or automatic recovery.

Invalid credential, locked account, unavailable path, observation failure, collision, cleanup failure, and host revocation remain distinct recovery categories. Public text is deliberately non-oracular. Switch starts with explicit successful update import, then performs the same inspection and one-attempt plan.

Credential save is off until current-user consent selects Save. It accepts only the exact selected server target and refuses wildcard, UNC, guessed, unmanaged, or overwritten targets. The first Save selection visibly selects reconnect by default; reconnect can then be cleared separately. A map uses an unused owner-selected `D` through `Z` letter and the exact UNC through a future in-process Windows API seam; no secret crosses a shell or child-process boundary.

## Narrow cleanup and verification

Unmap and credential deletion address only the current-user record's exact letter, UNC, and separately recorded provider target. Defined not-found cases succeed; no operation force-disconnects or guesses a wildcard target. Verification owns one unique `.ballsserver-verify-<operation>.tmp` file and, in order, creates, writes, reads/compares, renames, and deletes it without enumerating existing files. A cleanup failure retains the exact owned leftover only in a private recovery view; public status and diagnostics do not disclose it.

Host revocation remains a host-side enforcement event. A stale client credential cannot convert revocation into access; local client cleanup is independent.

## Guarded future harness

The future provider/credential and mapping harness is eligible only with an administrator, a non-development host, a disposable-VM marker, a known snapshot ID, and a `BallsServer.Test.` namespace. Development-host/default execution refuses without calling any native adapter. The isolated planner and tests are the v0.3 evidence only; actual provider-target consumption, mapping, reconnect, collision, cleanup, and host-revocation behavior require the later opt-in disposable-VM suite.
