# v0.3.0 ledger, reconciliation, rollback, and recovery contract

Status: isolated design and platform-neutral prototype evidence for Ticket 04. This contract authorizes no production helper, Windows adapter, or mutation.

The binding [v0.3.0 specification](../../.scratch/v0.3.0/spec.md), [threat model](v0.3.0-threat-model.md), and [operation matrix](v0.3.0-operation-matrix.md) remain authoritative. The [privileged-helper contract](v0.3.0-privileged-helper-boundary.md) supplies authorization, and the [managed-resource contract](v0.3.0-managed-resource-safety.md) supplies exact resource identities and fingerprints. This document narrows OP-03, OP-04, OP-23, OP-24, and OP-39 without expanding any operation.

## Authority and isolation

The protected ledger is evidence, never authorization. A record cannot substitute for current observation, the one-shot helper's authenticated peer evidence, its exact user/session/operation/revision/nonce/plan-digest/pipe/helper-instance binding, or its helper-owned Apply lease. Journaled consent is historical evidence only. Every later mutation still requires a fresh OP-02 request, authoritative re-observation, matching digest, and one-use helper-controlled confirmation.

No live `managed` Boolean, friendly name, description, apparent equivalence, audit record, recovery manifest, or user-writable copy can self-attest ownership. A resource is product-owned only when protected ledger evidence supplied independently of the live observation binds the exact stable identity, canonical fingerprint, product marker, owning operation, revision, and helper observation context defined by Ticket 03.

The executable model remains under `.scratch/v0.3.0/prototypes/ledger-recovery*`. It is absent from `BallsServer.slnx`, `src/`, and production composition. It uses only in-memory values; it has no elevation, IPC, shell, Windows API, filesystem fixture, network client, account/group/ACL/share/firewall adapter, credential or mapping adapter, managed-folder access, or mutating VM path.

## Protected host ledger schema v1

Schema version `1` is the only accepted version. Unknown older or newer versions, missing fields, duplicate JSON keys, malformed encodings, invalid enums, negative or non-monotonic revisions, weak ACLs, and failed integrity checks refuse. v0.3.0 defines no migration routine: a later migration requires a separately versioned, reviewed, crash-tested operation. It may never reinterpret an unsupported file in place.

The complete logical document is:

| Field | Exact content and rule |
| --- | --- |
| `schemaVersion` | Integer `1`. |
| `productHostId` | Opaque random product host identity; never an SMB/DNS name. |
| `hostStableId` | Canonical non-secret host identity fingerprint from an approved later Windows observation. |
| `ownerSid` | Canonical initiating owner SID; private local data, not a password-derived identifier. |
| `revision` | Signed 64-bit non-negative monotonic revision. A commit accepts exactly prior committed revision plus one. |
| `desiredStateFingerprint` | SHA-256 fingerprint of the complete canonical desired resource set and policy version. |
| `managedFolder` | Resource record containing volume/file stable identity, canonical descriptor fingerprint, OP-06, product marker, and helper observation context. The path is protected private data and redacted from default diagnostics. |
| `resources[]` | Exact protected host resource records for group, ACE, share, firewall rules, grants, attributable sessions, and verification leftovers when applicable. Current-user mappings and provider credential targets are excluded. |
| `endpoints[]` | Endpoint kind, private value fingerprint, observation epoch, and helper context. A snapshot is drift-prone and cannot authorize a connection or fallback. |
| `journal[]` | Append-oriented operation and primitive records described below. |
| `auditReferences[]` | Opaque audit ID, timestamp, and chain hash only; the referenced audit payload remains separate append-oriented protected evidence. |
| `tombstones[]` | Revoked grant ID, account stable ID, credential revision, revocation time, host-removal time, and audit reference. No password or password-derived data. |
| `hostRemovedAt` | Authenticated terminal host-removal timestamp or absent while configuration is active. It starts the 90-day retention clock. |

Each protected host `resources[]` record contains exactly `kind`, `stableId`, `canonicalFingerprint`, `owningOperation`, `ownershipMarker`, and `contextBinding`. Its closed `kind` enum has no mapping or provider-credential member. The owning-operation map is exact: managed folder/OP-06, group/OP-07, ACE/OP-08, share/OP-09, LAN firewall rule/OP-10, Tailscale firewall rule/OP-11, grant/OP-12, attributable session/OP-16, verification file/OP-32, and verification-file cleanup/OP-38. OP-39 owns retention purge rather than a Windows resource. Mapping identity, UNC fingerprint, and provider target fingerprint exist only in the separate current-user intent record.

Each journal record contains the exact `balls-helper/1` protocol version, defined operation enum and operation ID, product host ID, request/base revision `N`, canonical plan digest, pipe-instance fingerprint, nonce fingerprint, consumed authorization-binding fingerprint, helper observation context, monotonic record sequence, prior-record hash, record hash, phase, closed result, timestamp, and consumed-authority Boolean. A committed snapshot is `N+1`. Planned, in-progress, verified, failed, unknown, succeeded, canceled, refused, and repair-needed results are valid only for their exact phases; rollback and recovery phases follow the state machine; and exactly one final `Completed`, `Canceled`, `Refused`, `RepairNeeded`, or `Unknown` record terminates a chain. A `RepairNeeded` handoff may instead continue through `Recovering`, in which case the later final record is the terminal record.

Those fields preserve the Ticket 02 binding for audit and replay refusal. They do not preserve an Apply lease, secret, or reusable authority. A helper restart, replay, recovery, or new mutation always needs fresh authorization.

The ledger, journal, audit, tombstones, and manifest explicitly exclude passwords, password-derived identifiers, password hashes, password-policy guesses, recoverable secret hints, setup-code payloads, credential blobs, QR or clipboard content, Tailscale credentials/keys, raw exception/command output, file listings, and user-file names or contents. Provider credential-target names and endpoint/folder values are non-secret private data: protected state may retain their exact canonical form when required, while default diagnostics use opaque fingerprints.

## Exact protected storage

Future host state uses these machine-wide logical paths beneath `%ProgramData%\Balls Server\State\`:

- `host-ledger.v1.primary` — canonical primary snapshot;
- `host-ledger.v1.mirror` — canonical mirror snapshot;
- `host-ledger.v1.journal` — append journal with hash chaining and monotonically increasing record sequence;
- `host-audit.v1.journal` — separate append-oriented non-secret audit evidence; and
- `host-recovery.v1.manifest` — latest explicitly previewed non-authoritative recovery manifest.

The directory and files are SYSTEM-owned and protected against inherited writable grants. After substituting the canonical owner SID, the required file SDDL is `O:SYG:SYD:P(A;;FA;;;SY)(A;;FA;;;BA)(A;;FR;;;<OWNER-SID>)`: SYSTEM and built-in Administrators have Full Access, the recorded owner has read access, and no ordinary user has write access. Only the elevated helper running as an administrator, Administrators, or SYSTEM can write. Every open verifies owner, DACL protection, exact ACE set, stable file identity, non-reparse path, local fixed NTFS storage, schema, length bounds, and integrity chain before parsing. Weak, inherited, user-writable, remote, reparse, inaccessible, or unobservable state is Unknown and read-only.

Primary and mirror are independent replace targets. A commit writes a uniquely named same-directory temporary file with the restrictive ACL, flushes file data and metadata, validates schema/hash/revision, and atomically replaces the target. The temporary name never carries user input. The journal is append-only: each bounded record is length-prefixed, closed-schema, sequence numbered, chained to the prior record hash, flushed before the next primitive, and never rewritten to erase an incomplete operation.

The current-user client-intent record is a separate per-profile store. It binds host/grant/revision to the exact mapping UNC and separately proven provider credential target. It is user-writable by design and can authorize only an explicitly consented current-user client action after fresh collision/endpoint checks. It is never host ownership proof, never copied into the protected host authority set, and never authorizes a privileged mutation.

## Atomic transaction and revision protocol

One future helper request uses one operation ID, idempotency key, expected revision, nonce, plan digest, helper instance, and terminal result. The durable order is exact:

1. Complete provisional preview, authoritative revalidation, and helper-owned consent under Ticket 02. No ledger record can bypass these steps.
2. Verify primary, mirror, journal, ACLs, schema `1`, equal committed revision, and exact current resource observations. A stale request stops with `Refused: stale revision`; the nonce is consumed and the dashboard must refresh.
3. Append and flush `Planned`, including request binding fingerprints, authoritative plan digest, expected revision, desired-state fingerprint, ordered primitive list, and before-state fingerprints.
4. Before each primitive, append and flush `Started:<index>` with the exact expected precondition and intended postcondition fingerprint.
5. Execute exactly one bounded typed primitive. Cancellation cannot interrupt the primitive.
6. Re-observe stable identity and every postcondition. Append and flush exactly one `Verified`, `Failed`, or `Unknown` record. Only `Verified` advances to the next primitive.
7. Honor cancellation between primitives. If rollback is safe, enter `RollingBack`; otherwise enter `Repair needed`. Each rollback primitive uses the same write-ahead and verification rule.
8. After every primitive verifies, build revision `N+1`; atomically replace and flush primary, then mirror, each with identical content hash and revision.
9. Append and flush the revision-commit record that authenticates both copy hashes and revision `N+1`. Only this record advances `committedRevision`.
10. Append and flush the terminal `Completed`, `Canceled`, `Repair needed`, `Refused`, or `Unknown` record, write one bounded terminal response, and exit. A lost response never becomes success; a later fresh reconciliation determines state.

A valid mirror can reconstruct one missing or corrupt primary; a valid primary can reconstruct one missing or corrupt mirror. The surviving copy and complete journal chain must agree on host ID, schema, revision, transaction states, and content hash. Reconstruction atomically replaces only the damaged protected copy, then revalidates both. Two valid divergent copies, an invalid journal, weak ACL, unsupported schema, or inconsistent revision is Unknown/read-only. If both primary and mirror are missing or corrupt, the journal is corroboration only and total-ledger-loss rules apply; it cannot recreate ownership authority by itself.

## Operation state machine

The platform-neutral state machine permits only these transitions:

| From | Allowed next states |
| --- | --- |
| `Preview` | `AuthoritativeRevalidation`, `Canceled`, `Refused`, `Unknown` |
| `AuthoritativeRevalidation` | `AwaitingHelperConsent`, `Canceled`, `Refused`, `Unknown` |
| `AwaitingHelperConsent` | `Planned`, `Canceled`, `Refused`, `Unknown` |
| `Planned` | `Started`, `Canceled`, `RepairNeeded`, `Unknown` |
| `Started` | `PrimitiveVerification`, `CancellationPending`, `RollingBack`, `RepairNeeded`, `Unknown` |
| `PrimitiveVerification` | `Started`, `CancellationPending`, `RollingBack`, `RepairNeeded`, `AtomicRevisionCommit` |
| `CancellationPending` | `RollingBack`, `Canceled`, `RepairNeeded` |
| `RollingBack` | `Canceled`, `RepairNeeded` |
| `AtomicRevisionCommit` | `Completed`, `RepairNeeded`, `Unknown` |
| `RepairNeeded` | `Recovering` |
| `Recovering` | `Started`, `RollingBack`, `Completed`, `Canceled`, `RepairNeeded`, `Unknown` |
| `Completed`, `Canceled`, `Refused`, `Unknown` | No transitions |

`Planned`, every primitive `Started`/verification result, each rollback result, both atomic copy replacements, revision advancement, and the terminal result are durable boundaries. Cancellation before the first primitive produces `Canceled` without mutation. Cancellation during a primitive becomes pending until that primitive is journaled and verified or failed. Cancellation never converts failed or uncertain rollback to success.

Idempotent replay of the same completed operation ID and exact plan digest returns the recorded terminal result with zero primitives. A digest mismatch, unknown operation, incomplete terminal, stale revision, or changed context refuses. A repeated conformant setup verifies without duplicate creation. A repeated removal treats absence as success only for the exact protected record at OP-24, OP-34, OP-36, OP-38, or recovery cleanup; setup and repair never coerce not-found to success.

## Deterministic reconciliation

Every desired resource receives exactly one classification from independent protected ownership evidence and one fresh complete live observation:

| Protected ownership evidence | Live observation | Classification |
| --- | --- | --- |
| Exact proof | Exact stable identity, context, and fingerprint | `OwnedConformant` |
| Exact proof | Exact stable identity/context but changed fingerprint | `OwnedDrifted` |
| Exact proof or no prior record | Unambiguous absence after complete enumeration | `Missing` |
| Exact proof | Different stable identity in the same slot or foreign object | `UnmanagedConflict` |
| No protected proof | Any present same-name/equivalent/live-managed object | `UnmanagedConflict` |
| Any non-corrupt proof | Multiple candidates, duplicate identities, or ambiguous marker | `Ambiguous` |
| Corrupt proof | Any observation | `Unknown` |
| Any proof | Access denied, policy override, incomplete/malformed/unavailable observation | `Unknown` |

`OwnedConformant` is a verified no-op. `OwnedDrifted` can enter object-specific repair only after a fresh preview and authorization; it is never overwritten automatically during recovery. Desired resource evidence is fully validated before `Missing` is possible. The reconciliation result carries protected, unowned, or invalid provenance into convergence; malformed desired evidence is `Unknown` and cannot create. A valid no-record/live-absence result remains explicitly unowned: desired-absent convergence preserves it and cannot report an owned removal or authorize cleanup. `UnmanagedConflict` and `Ambiguous` refuse and preserve the object. `Unknown` performs no mutation.

The classifier ignores a live friendly name, description, product-like marker, or `managed=true` claim. It never adopts or normalizes an equivalent object. Every resource uses the stable proof of its owning operation; no generic name-based rule weakens Ticket 03.

## Crash injection and recovery matrix

The in-memory prototype injects a crash immediately before and after every planned-journal append, primitive-start journal append, primitive, primitive-verification journal append, primary atomic replacement, mirror atomic replacement, and committed-revision advancement. For a three-primitive plan this is 26 distinct injection points. Its durable snapshot contains a closed typed, ordered plan/journal rather than free-form strings; unknown, extra, duplicate, or reordered records are refused. Recovery consumes only that snapshot, never the caller-known injection point. Revision `long.MaxValue` returns a typed exhausted refusal before arithmetic. Every ordinary run starts from revision `N`, applies only in-memory stable IDs, stops at the selected point, and returns one recovery disposition:

| Injection point | Durable/live state after crash | Recovery result |
| --- | --- | --- |
| Before `Planned` | No transaction record and no live change | Restart from a fresh preview and authorization. |
| After `Planned`; before/after a primitive `Started`; before a primitive | Planned or started record, no unrecorded primitive effect at that point | Read-only reconcile all prior verified primitives and this exact resource; fresh authorization is required to continue or roll back. |
| After a primitive; before its verified record | Exact primitive may have occurred but is not proven | Re-observe its stable identity and expected postcondition. Exact match may be journaled during authorized recovery; drift, foreign, ambiguous, denied, or unknown becomes `Repair needed`/`Unknown`. |
| Before/after primitive verification journal | Live object and journal may disagree by one verification record | Reconcile exact object and hash chain; never rerun based only on intent. |
| Before/after primary or mirror replacement | Zero, one, or both snapshot copies may contain `N+1`; committed revision remains `N` | Select only an authoritative equal-schema/hash history, rebuild the one damaged/stale copy, then revalidate. Divergence remains read-only. |
| Before revision advancement | Both copies may contain `N+1`, but commit marker remains `N` | Verify identical copies and full journal before an authorized recovery records `N+1`; do not rerun primitives. |
| After revision advancement | Primary, mirror, and commit marker are `N+1` | Return completed idempotently with zero primitives after fresh read-only verification. |

Every crash recovery starts read-only. Every later mutation, including completing a protected-state repair or rollback, requires fresh helper authorization. No crash disposition allows the ledger to authorize itself, adopt an object, overwrite drift, delete by name, or delete the managed folder or user files.

## Rollback, repair, and removal

Rollback walks successfully applied primitives in reverse order. It removes an object only when all are true:

1. the journal proves this exact operation created it;
2. the stable live identity equals the captured post-create identity;
3. the complete live fingerprint and context equal the captured postcondition;
4. no foreign dependency, active use, policy override, ambiguity, or access denial exists; and
5. the owning operation defines an exact inverse that preserves unrelated state.

If any predicate fails, rollback preserves the object and enters `Repair needed` with object-specific guidance. It never restores a broad snapshot, overwrites drift, takes ownership, replaces a DACL, edits an unmanaged equivalent, force-disconnects work, closes unlisted sessions, deletes by friendly name, or deletes the managed folder or any user file.

Setup convergence is exact: conformant means verify/no change; missing means at most one creation after conflict scan and fresh authorization; drift is repair-needed; conflict/ambiguity refuse; unknown stays unknown. Removal convergence is exact: a proven-owned absence is terminal success only at the documented removal/recovery point. Access denied, policy management, changed identity/fingerprint, malformed state, or incomplete observation is never not-found and never success.

## Exact scenario outcomes

| Condition | Automatic result | Required recovery |
| --- | --- | --- |
| Stale revision | Refused; nonce consumed; zero mutation | Refresh observation and preview, then request new authorization. |
| Corrupt/missing primary with valid mirror and journal | Protected-state repair only; no Windows mutation | Atomically rebuild primary from mirror, verify equality, then re-observe resources. |
| Corrupt/missing mirror with valid primary and journal | Protected-state repair only; no Windows mutation | Atomically rebuild mirror from primary, verify equality, then re-observe resources. |
| Two valid divergent copies or invalid journal | Unknown/read-only | Administrator preserves files; product reports hashes/revisions through redacted evidence and waits for reviewed recovery. |
| Total ledger loss | All product automation read-only | Produce the non-authoritative manifest below; administrator confirms every object independently. |
| Owned drift | `OwnedDrifted`; no overwrite | Fresh object-specific repair preview or manual recovery. |
| Missing object | `Missing` | Recreate once only when stable absence and namespace are unambiguous; otherwise preserve/refuse. |
| Unmanaged conflict | `UnmanagedConflict`; Refused | Preserve object and resolve outside Balls Server or choose a nonconflicting approved state. |
| Ambiguity | `Ambiguous`; Refused | Administrator distinguishes stable identities; no adoption or fuzzy cleanup. |
| Access denial | `Unknown`; zero mutation | Responsible administrator restores read access or inspects the exact object, then re-observe. |
| Policy override | Refused; zero override | Responsible GPO/policy owner resolves the exact setting, then re-observe. |
| Unknown observation | `Unknown`; zero mutation | Complete the named observation; do not infer, retry, or broaden. |

## Total-loss recovery manifest

When primary and mirror are both missing or corrupt, all host repair, setup, removal, and adoption automation becomes read-only. Read-only probes may inventory candidate product markers, but the generated manifest is explicitly `authoritative=false`, `authorizesAdoption=false`, and `authorizesDeletion=false`. Each item contains only resource kind, observed stable ID, observed non-secret fingerprint, observation status, and an instruction requiring administrator confirmation against Windows.

The object-by-object order is:

1. grants: match grant ID evidence to account SID, flags, group membership, and credential revision; disable and remove membership manually only after exact confirmation;
2. attributable sessions: match session stable ID, account SID, client, and share before any explicit closure;
3. share: match stable share identity, exact folder volume/file identity, and descriptor; remove only the share object, never its directory;
4. firewall rules: match policy store, stable rule ID, full direction/protocol/TCP 445/profile/interface/address expression;
5. ACE: match folder volume/file identity, group SID, binary ACE tuple, owner/control flags, and unchanged unrelated-ACE multiset; remove one ACE only;
6. group: match SID, stable object ID, marker, rights, memberships, and remaining dependencies;
7. each affected current-user profile: match drive/full UNC, then the separately recorded provider target and qualified SAM identity; host cleanup cannot perform this remotely; and
8. verification leftovers: match exact path, operation ID, file identity, prefix, and known non-secret marker before deleting that one product-created file.

The managed folder appears only as preserved identity context. The manifest never instructs deletion, movement, ownership change, DACL replacement, enumeration, or content cleanup for the folder or user files. Any mismatch preserves the object. A later reconstructed or reinitialized ledger does not adopt survivors; ownership must be re-established through a separately approved design.

## Audit, redaction, and 90-day retention

Audit remains local and append-oriented. Each event records timestamp, opaque operation/grant/correlation IDs, actor SID/category, ledger revision, phase, resource kind and stable-ID fingerprint, preview/consent state, before/after non-secret fingerprints, result category, rollback/recovery decision, and bounded native error code. It excludes secrets and raw private payloads. Default export also redacts owner/account/host names, SIDs, endpoint values, UNC roots, IPs, drive letters, managed-folder path, file names, and raw ledger contents unless the owner explicitly previews inclusion.

Revoked-grant tombstones, audit events, and superseded recovery evidence are retained until exactly `hostRemovedAt + 90 days`. Each retained record is a closed tuple of defined record kind, canonical opaque retention ID, authenticated removal time, and canonical non-secret evidence fingerprint; it cannot carry arbitrary payload bytes. At times earlier than that boundary records remain structurally and serialization-identical. At the exact boundary and afterward they are eligible for purge only when the protected timestamp/chain is valid, the clock is trusted, access is available, and no active reference remains. Clock ambiguity, a time before removal, corrupt chain, access denial, active reference, malformed fingerprint, or secret-shaped payload produces `Cleanup needed` and preserves the record. Repeated purge leaves expired records absent and unexpired/active records identical. Purge touches no active ledger, Windows resource, credential, managed folder, or user file and never retains a password, secret, or password-derived identifier.
