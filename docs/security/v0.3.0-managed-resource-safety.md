# v0.3.0 managed-resource safety contract

Status: isolated design and prototype evidence for Ticket 03. This contract authorizes no Windows or production mutation.

The binding [v0.3.0 specification](../../.scratch/v0.3.0/spec.md), [threat model](v0.3.0-threat-model.md), and [operation matrix](v0.3.0-operation-matrix.md) remain authoritative. This document makes the OP-05 through OP-11 safety model executable without adding it to `BallsServer.slnx`, `src/`, or production composition.

## Isolation boundary

The prototype is a platform-neutral model under `.scratch/v0.3.0/prototypes/managed-resource-safety/`. It exposes observations, immutable plans, verification results, typed refusals, and one disposable test-folder utility. It has no Windows mutation adapter, elevation path, helper integration, shell, service, listener, scheduler, account/group manager, ACL writer, share API, firewall API, policy API, network client, or managed-folder content operation.

The only real filesystem fixture uses a unique `BallsServer.Test.<32-lowercase-hex>` directory beneath the operating-system temporary directory. Its owner object deterministically removes that exact directory. The tests create only one known non-secret file inside it and prove the directory is absent after disposal. No real managed-folder candidate is read or written.

## Managed-folder validation and TOCTOU

OP-06 retains an immutable tuple of volume ID, directory file ID, canonical final path, and descriptor fingerprint. It also retains the sorted descendant-link observations: relative path, canonical absolute link-object path, canonical final target path, exact target volume ID, closed target evidence, and distinct stable link-object and target-object identities. Those values come from a typed read-only observation seam; the model never resolves or follows a live target itself.

Validation refuses before any later primitive when the candidate is missing, not a directory, remote, a device path, a drive root, protected system state, not fixed local storage, non-NTFS, root-reparse, ancestor-reparse, incompletely scanned, or contains a descendant link whose target, volume, or stable identity cannot be resolved. At the final decision boundary it independently revalidates the canonical absolute root, link-object, and target paths, recomputes the link path from the root and relative descendant, recomputes target segment containment, and requires exact root/target volume identity plus distinct nonempty link-object and target-object IDs. Caller-reported containment Booleans are non-authoritative. Canonical validation rejects traversal segments, alternate-data-stream syntax, device/noncanonical namespaces, reserved names, trailing-dot/space aliases, and a different target volume before comparing case-insensitive Windows path segments. Relative descendant paths use forward slashes only, with no duplicate, mixed, rooted, or trailing separator, and the retained sequence must already equal discovery's ordinal sort. Link discovery enumerates directories without descending through a discovered link. A contained resolved link is retained as drift-sensitive evidence; it is not followed.

Immediately before use, the helper must independently re-observe the complete tuple and descendant-link sequence. The retained result itself must be the one canonical success tuple: Accepted, defined `None` refusal, empty guidance/mutations, complete closed identity, and unique descendant link paths/link-object IDs whose complete target evidence independently passes the final canonical containment rule. A contradictory success Boolean, undefined/non-None refusal, guidance, mutation, incomplete identity/link, or duplicate evidence refuses before comparison. Any path, volume, file, descriptor, link, target, containment, scan, or stable-identity difference is `IdentityDrift`: apply nothing and rebuild the authoritative plan. No refusal takes ownership, replaces a DACL, walks into a reparse target, recursively rewrites children, deletes a directory, or changes a user file.

## Exact product group and NTFS ACE

The single access group has the fixed friendly name `Balls Server Access`, but a name or description never proves ownership. The protected ledger must bind its SID, stable Windows object ID, and exact product marker to the live object. Any missing, changed, same-name, equivalent, foreign, or ambiguous identity is an unmanaged conflict and is never adopted, edited, renamed, deleted, or treated as equivalent.

The one product NTFS ACE is exactly:

| Field | Exact value |
| --- | --- |
| Type | Allow |
| Trustee | exact product-group SID |
| Rights | Modify plus Synchronize |
| Inheritance | Container inherit plus Object inherit |
| Propagation | None |
| Inherited | False |

The planner preserves the descriptor owner and DACL control flags. It fingerprints the canonical multiset of every unrelated ACE, including duplicate multiplicity, before adding one exact product ACE. The complete same-product-SID multiset must contain exactly one entry and that entry must equal the recorded exact ACE. A same-SID deny, rights/inheritance/propagation/inherited variant, unowned exact ACE, or duplicate exact ACE refuses during apply verification, owned idempotency, and removal.

The proposed-rights intent maps the exact ACE to the required create/read/write/rename/delete operations but does not claim Windows effective access. A separate fresh before/after effective-access observation must be available and not access-denied for exactly the product group, retained owner, SYSTEM (`S-1-5-18`), and Administrators (`S-1-5-32-544`). It proves the product group has exactly Modify plus Synchronize, with no excess rights, and that owner/SYSTEM/Administrators retain their prior control access; unavailable, denied, identity-mismatched, insufficient, excessive, or drifted results fail closed. Removal requires the exact recorded group SID and ACE plus unchanged owner, flags, and unrelated multiset, and reconstructs the exact prior descriptor. It removes no other ACE and never restores a broad ACL snapshot over changed state.

## Fixed share and compliant SMB prerequisite

The only proposed share name is `Balls`. Creation receives the final descriptor in its first and only create step: the Administrators well-known SID (`S-1-5-32-544`) Full, product group Change, and no Everyone, Guest, Anonymous, blank-password, or other principal. There is no broad or permissive intermediate share state. One reusable closed desired-state validator governs both planning and final accepted-plan verification. It requires exact share/group product markers; canonical decimal SID spelling; group and grant SIDs with one identical local-machine prefix and distinct RIDs; distinct nonempty stable object IDs; a closed folder volume/file/path/descriptor identity; positive revision and observation epoch bounded to the supported sequence range; and a helper-owned authorization token with exactly one nonzero 32-lowercase-hex nonce suffix. Textual aliases of one Windows SID, a cross-machine grant, or reused stable identity refuse. Repeating malformed/default values across a forged plan and its contexts cannot authorize success. A share observation cannot attest its own ownership. The protected ledger record is supplied independently and its canonical fingerprint binds the fixed name, stable share object ID, retained folder identity and descriptor, exact ordered permission set, product marker, and revision. A newly created ownership record is captured only after exact live verification.

Success is a distinct authorization-intersection result that binds the exact stable share and descriptor to freshly verified folder identity/use, exact ACE, before/after effective access, still-compliant SMB prerequisites, and limited-grant behavior. One helper-owned observation token and monotonic epoch bind every input to the same authoritative observation context, exact plan revision, folder volume/file/descriptor identity, group SID/object identity, fixed share name/stable ID/descriptor fingerprint, and expected grant SID/object identity. Each component must carry the canonical success tuple: `Accepted` plus its exact ready/no-refusal code; a contradictory success Boolean with any refusal code is rejected. The limited grant must read and change through the share while guest, anonymous, and blank-password access all remain ineffective. Stale, cross-resource, drifted, contradictory, or failed input refuses and captures no ownership.

An existing name, folder, marker, permission set, stable identity, or apparently equivalent share without exact ledger ownership is a conflict. Balls Server never adopts, widens, edits, renames, removes, or suffixes it.

The SMB and Server-service state is observe-only. Setup refuses unless observation proves all of these together: Server running; SMB1 disabled; SMB 2/3 enabled; complete, ordered, known minimum/maximum dialect bounds with a minimum of SMB 3.0; signing preserved; no guest, anonymous, or blank-password acceptance; and no unknown or policy-managed value. Null, incomplete, malformed, unknown, or inverted dialect bounds are Unknown, never Accepted. The share plan preserves the exact typed refusal and deterministic administrator handoff for each failed prerequisite, followed by a fresh read-only observation. Balls Server never changes SMB, signing, encryption, Server service, user rights, or policy.

## Private TCP 445 rule plans

LAN and Tailscale use distinct stable product rule IDs and never share or adopt a rule:

| Plan | Exact scope |
| --- | --- |
| LAN | Enabled inbound TCP 445, one stable local interface, Private or Domain profile, LocalSubnet remote scope |
| Tailscale | Enabled inbound TCP 445, one stable observed Tailscale interface, Private or Domain profile, documented private Tailscale ranges |

Each immutable canonical rule expression includes stable ID, fixed name, enabled state, Allow action, local persistent policy store, product marker/revision, inbound direction, TCP protocol, port 445, Private/Domain profile, one stable interface, a helper-owned observation token/epoch, and concrete local and private remote address ranges. CIDRs are parsed with real IPv4/IPv6 address and prefix math and must use one canonical textual form. Local scope is a concrete selected-interface host address. LAN remote scope equals that interface's freshly observed canonical private subnet; Tailscale remote scope equals the exact approved freshly observed private ranges. Whitespace aliases, invalid octets, `/0`, host-as-subnet, wildcard, supernet, public, loopback, link-local, multicast, unspecified, cross-interface, and stale-context ranges refuse. A separate protected-ledger ownership record binds stable live object ID, marker/revision, and the fingerprint of every expression field; no live `managed` Boolean is trusted. Both plans reject disabled or Block rules, Public or Any profiles, Any remote/local addresses, Any interfaces, any protocol, non-445 ports, outbound direction, ambiguous interface/profile/effective-state evidence, built-in rules, unmanaged/equivalent rules, Group Policy-owned stores, absent Tailscale evidence, and a scope that cannot be expressed or re-observed exactly. Rule verification compares the independent ledger record, stable object identity, and every configuration field. Undefined path, policy, rule-expression, status, or refusal enum values fail closed as Unknown or refusal. It never changes a built-in group, unmanaged rule, firewall default, profile category, interface, route, Tailscale state, router, cloud edge, or public policy.

## Exact administrator handoffs

- Server stopped: restore the Windows Server service outside Balls Server, then re-run read-only observation.
- SMB1 enabled: disable SMB1 outside Balls Server, then re-run read-only observation.
- SMB 2/3 unavailable: enable the supported SMB 2/3 server capability outside Balls Server, then re-run read-only observation.
- Minimum dialect below SMB 3.0: require a minimum dialect of SMB 3.0 outside Balls Server, then re-run read-only observation.
- Signing not preserved: restore signing protections outside Balls Server, then re-run read-only observation.
- Guest, anonymous, or blank-password SMB acceptance: have the administrator restore authenticated-only SMB outside Balls Server, then re-run read-only observation.
- Policy-managed SMB state: ask the responsible policy owner to prove a compliant setting; Balls Server will not override it.
- Unknown or incomplete SMB state: complete the unavailable dialect, service, and policy observations; uncertainty cannot authorize setup.
- Policy-managed firewall state: ask the responsible Group Policy owner to provide a writable product-specific rule store; Balls Server will not override policy.
- Unknown firewall effective state: complete the unavailable policy and effective-state observations; uncertainty cannot authorize a rule.
- Ambiguous interface: identify one stable Private or Domain interface with exact local and private remote address ranges, then re-observe.
- Unexpressible scope: provide a policy store that expresses every exact narrow field; no broader rule is allowed.
- Built-in or unmanaged conflict: preserve the object and use the named manual-recovery path; it is never adopted.
- Public/broad expression: correct the proposal to one enabled Allow inbound TCP 445 rule over exact private interface and address scope; Public or Any remains refused.
- Missing Tailscale evidence: complete the Tailscale-owned install/sign-in flow, then re-run read-only observation. No Tailscale credential enters Balls Server.

## Later mutation-test gate

A later mutation runner is eligible only after every independent guard proves explicit opt-in, administrator execution, a disposable-VM marker, a known-restorable snapshot identity, a unique namespace strictly below `BallsServer.Test.`, and no production identity in scope. A development-host marker always refuses. Ticket 03 tests only each denial and exposes no executor; it does not run the all-green branch against Windows and does not perform a mutating VM case.

The later VM suite must still use a dedicated temporary NTFS folder, before/after unrelated-state inventories, snapshot restore or discard, and exact data-survival evidence. Passing this pure guard is necessary but never sufficient authorization for a Windows primitive.

## Public result boundary

The denial-only prototype formats `Verified` only for the exact closed tuple `Accepted=true` plus the defined `ResourceRefusal.None`. `Accepted=true` with any non-None or undefined refusal, and `Accepted=false` with None or an undefined refusal, formats a redacted Unknown result. Defined refusal tuples format Refused. No public formatter includes paths, SIDs, contexts, ownership data, or caller diagnostics.
