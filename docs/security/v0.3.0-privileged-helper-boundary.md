# v0.3.0 privileged-helper authorization boundary

Status: isolated design and feasibility prototype. This contract authorizes no production helper or Windows mutation.

The binding authorities are the [v0.3.0 specification](../../.scratch/v0.3.0/spec.md), [threat model](v0.3.0-threat-model.md), and [operation matrix](v0.3.0-operation-matrix.md). This document narrows their OP-02 seam without expanding the approved operation inventory.

## Permanent boundary

The dashboard remains unelevated. It can create one local IPC endpoint, launch one helper through `ShellExecuteEx` with the `runas` verb, authenticate that helper, send one request, receive one terminal response, and close. It cannot mutate host state or assert privileged consent.

The future helper is a separate signed, elevated, on-demand executable for one request. It is not a service, scheduled task, installer, listener, shell, PowerShell host, arbitrary command runner, or general administration channel. It canonicalizes identifiers, re-observes state, computes the authoritative plan, owns the confirmation UI, consumes one Apply decision, executes only a typed operation inventory, writes one terminal response, and exits.

UAC answers only whether Windows may start an elevated process. It does not authorize a Balls Server operation. A dashboard preview, checkbox, button, approval field, or caller claim is also insufficient. Only the helper-controlled authoritative Apply decision described below authorizes one request.

## Exact pipe construction

The dashboard generates 128 random bits and creates `\\.\pipe\BallsServer.Helper.v1.<32-lowercase-hex>` before launching the helper. The name is an address, not a secret, and is the only per-run value permitted in the helper command line. No nonce, plan, identity, path, or secret is passed as an argument or environment value.

Production construction uses `CreateNamedPipeW` with:

- `dwOpenMode = PIPE_ACCESS_DUPLEX | FILE_FLAG_FIRST_PIPE_INSTANCE | FILE_FLAG_OVERLAPPED`;
- `dwPipeMode = PIPE_TYPE_BYTE | PIPE_READMODE_BYTE | PIPE_WAIT | PIPE_REJECT_REMOTE_CLIENTS`;
- `nMaxInstances = 1`;
- `nOutBufferSize = 16384`, `nInBufferSize = 16384`, and `nDefaultTimeOut = 5000` milliseconds;
- a non-inheritable handle; and
- this exact SDDL after replacing `<SID>` with the initiating token's canonical SID: `O:<SID>G:SYD:P(A;;GA;;;<SID>)(A;;GA;;;BA)(A;;GA;;;SY)S:(ML;;NW;;;ME)`.

The protected DACL grants only the initiating user, built-in Administrators, and SYSTEM. The medium mandatory label permits the elevated helper to write down while preventing a lower-integrity peer than the dashboard. `FILE_FLAG_FIRST_PIPE_INSTANCE` turns a pre-existing name into an immediate refusal, and `PIPE_REJECT_REMOTE_CLIENTS` rejects network pipe clients. ACL membership is only endpoint access; it is never peer authorization.

The dashboard records its pipe handle, process ID, process creation time, user SID, and interactive session before launch. It launches exactly the protected installed helper path. The helper connects as the pipe client. Neither side transmits application data until both sides complete the evidence checks below. If a squatter connects, identity is unverifiable, a peer dies, or any API returns incomplete evidence, the endpoint is closed and the helper exits without reading a request.

## Mutual peer evidence

The dashboard obtains the helper PID with `GetNamedPipeClientProcessId`; the helper obtains the dashboard PID with `GetNamedPipeServerProcessId`. Each opens the peer with `PROCESS_QUERY_LIMITED_INFORMATION | SYNCHRONIZE`, captures `GetProcessTimes` creation time as the process-instance discriminator, and rechecks liveness with a zero-time `WaitForSingleObject` after all other checks. PID reuse, access denial, an exited handle, or a changed instance fails closed.

Each peer opens the process token with `TOKEN_QUERY` and checks `TokenUser`, `TokenSessionId`, `TokenIntegrityLevel`, `TokenElevation`, and `TokenElevationType`:

- both tokens must have the initiating SID and interactive session ID;
- the dashboard must be medium integrity, not elevated, and as-invoker;
- the helper must be high integrity with a full elevated token; and
- a different user, session, integrity, elevation type, or unavailable token field is refused.

Each side checks `QueryFullProcessImageNameW`, opens that exact image without following a caller-supplied path, rejects a reparse or non-file identity, and requires its expected file ID, product file version, SHA-256 digest, and Authenticode identity. Production authorization requires the exact `%ProgramFiles%\Balls Server\` manifest path, administrator/SYSTEM-owned and administrator-protected parent and file DACLs, a manifest-pinned digest/version, a successful `WinVerifyTrust` chain under current policy, and the release-publisher leaf certificate thumbprint pinned by the installed manifest. Path, metadata, hash, signer, or liveness uncertainty is refusal.

The dashboard verifies the helper before sending the request. The helper verifies the dashboard before reading it. The dashboard then rechecks helper liveness immediately before write; the helper rechecks dashboard liveness immediately before read. Authentication state belongs to this pipe handle and these two process creation times and cannot transfer to another connection.

## Strict protocol v1

Every UTF-8 JSON message is length-prefixed by an unsigned 32-bit little-endian byte count. The count and payload must each arrive within their deadline. The maximum request and terminal-response payload is 16,384 bytes. Duplicate keys, invalid UTF-8, invalid JSON, omitted required fields, `null`, unknown fields, unknown enum values, overflow, and trailing bytes are refused; fields are case-sensitive. There is no extension bag.

The one allowed request message is:

```text
protocolVersion: "balls-helper/1"
messageType: "authorize"
operation: "OP-02", the only allowed enum value in this isolated proof
operationId: 1..64 ASCII characters, unique per owner action
nonce: exactly 32 random bytes encoded as 64 lowercase hex characters
expectedRevision: signed 64-bit non-negative ledger revision
provisionalPlanDigest: SHA-256 canonical-plan digest as 64 lowercase hex characters
initiatingUserSid: canonical SID matching both authenticated peers
sessionId: non-negative interactive Windows session ID matching both peers
deadlineMonotonic: exactly helper launch monotonic time plus 180 seconds; a caller cannot extend it
```

This v1 proof is closed to exactly those ten fields. It deliberately carries no desired resource or Windows primitive, so it cannot become a mutation request. Every future operation must add one separately versioned closed resource schema before implementation; display strings, ACL text, arbitrary principal names, command text, and caller-supplied secrets remain forbidden. A request is bound to protocol, operation enum, operation ID, nonce, revision, user, session, peer process instances, and the connected pipe. A nonce is consumed when a structurally valid request reaches authoritative re-observation, whether the later result completes or refuses; replay never retries.

The one allowed response message is:

```text
protocolVersion: "balls-helper/1"
messageType: "terminal"
operationId: exact request operation ID
nonce: exact request nonce
status: completed | canceled | repairNeeded | refused | unknown
code: one closed string-valued product result enum; integers, undefined values, and raw native text are forbidden
publicMessage: the exact bounded code-to-template text; caller-controlled text is forbidden
authorizedOperationCount: 0 or 1
systemMutationCount: exactly 0 in v0.3
secretPayload: absent except the separately defined OP-17 one-response envelope
```

Unknown fields, duplicate fields, integer or undefined enums, negative or out-of-range counts, invalid status/code/count combinations, oversized envelopes, and response binding mismatches are refused by the dashboard. The codec uses an exhaustive positive mapping: `completed` pairs only with `None` and one authorization; `Cancelled`, `RequestTimedOut`, or `ConsentExpired` pair only with `canceled` and zero; `Crashed` pairs with `repairNeeded` and one after journal initialization or with `unknown` and zero before it; and each explicitly enumerated ordinary-denial code pairs only with `refused` and zero. In particular, expiry can never be encoded or decoded as `refused`. The codec derives `publicMessage` from that typed pair through an exact allow-listed template. Caller text, paths, SIDs, account or host names, UNC roots, IP addresses, ACLs, stdout, stderr, exception text, command output, passwords, setup-code contents, credential blobs, and file listings cannot enter it. An unconfirmed dashboard `unknown` outcome is explicitly marked not delivered and cannot be encoded as a helper terminal. OP-17 may carry one bounded secret payload only after successful peer authentication and the exact authorized grant operation; the receiver can atomically take it once, no second terminal or secret response is possible, and both peers clear their buffers during terminal cleanup.

## Time and cancellation bounds

All durations use the following canonical helper-owned monotonic timeline; wall-clock changes and caller values cannot extend authority:

- `PipeCreatedAt` to `HelperLaunchedAt`: 10 seconds;
- `DashboardEvidenceStartedAt` to `DashboardEvidenceCompletedAt`: 5 seconds;
- `HelperEvidenceStartedAt` to `HelperEvidenceCompletedAt`: 5 seconds;
- `HelperLaunchedAt` to `MutualAuthenticationCompletedAt`: 15 seconds total;
- `RequestLengthReadStartedAt` to `RequestLengthReadCompletedAt`: 5 seconds;
- `RequestBodyReadStartedAt` to `RequestBodyReadCompletedAt`: 5 seconds;
- `ReobservationStartedAt` to `ReobservationCompletedAt`: 30 seconds per typed operation unless that operation publishes a narrower bound;
- `PlanDisplayedAt` to `ApplyAt`: 120 seconds;
- `TerminalWriteStartedAt` to `TerminalWriteCompletedAt`: 5 seconds; and
- `HelperLaunchedAt` to `TerminalWriteCompletedAt`: 180 seconds absolute.

Every start follows the preceding completion, and every phase is validated independently. Terminal completion, not merely Apply, must occur by the absolute lifetime. The request's `deadlineMonotonic` must equal `HelperLaunchedAt + 180`; an earlier, later, negative, or overflowing caller value refuses and can never loosen a helper-owned bound. After mutual authentication, every candidate outcome—including malformed request, binding failure, replay, stale revision, cancellation, timeout, consent failure, crash mapping, and completion—passes through the same one-use terminal-emission gate. The first emission attempt atomically and irreversibly claims that gate before candidate or timing validation, so a null, invalid, premature, late, lost, or concurrent first attempt closes the operation and no later write can deliver. A candidate is counted as delivered only after it satisfies the complete closed external-result contract, starts no earlier than its helper-owned ready timestamp, finishes within 5 seconds, completes by `HelperLaunchedAt + 180`, and wins the separate delivered-response gate. Failure of any emission check or a second write exposes only an unconfirmed dashboard `unknown`/no-response outcome; it never reports a delivered cancellation, refusal, repair requirement, or completion. Pre-authentication peer refusal closes the unauthenticated channel directly and does not claim an authenticated terminal delivery. Cancellation before journal preparation returns external `canceled` and performs nothing only when that terminal is confirmed. Cancellation between future primitives is honored after the current bounded primitive is journaled and verified or failed. A phase timeout or expired Apply similarly returns confirmed `canceled`; it closes the pipe, makes the authorization unusable, and never causes retry, fallback, or another endpoint. The dashboard displays unconfirmed `unknown` if the helper crashes before the journal or a terminal write is lost; it cannot infer success.

## Authoritative plan and one-use consent

After request validation, deadline binding, and authenticated user/session binding, the helper atomically consumes the nonce as authoritative re-observation begins. It independently canonicalizes every identifier and re-observes all required state. A stale revision therefore consumes the nonce and cannot later succeed. The helper constructs the canonical authoritative plan and SHA-256 digest. A revision or digest difference returns external `refused` with its bounded typed reason, performs no mutation, and requires a new dashboard observation and owner action.

A matching digest still authorizes nothing. The elevated helper displays a TaskDialog-style confirmation in the initiating interactive session with the authoritative changes, retained objects, consequences, interruption behavior, and recovery. Its Apply control creates one in-memory consent lease bound to:

- the helper PID and process creation time;
- initiating user SID and session ID;
- operation enum and operation ID;
- request nonce;
- expected revision and authoritative plan digest;
- this pipe instance; and
- a 120-second monotonic expiry.

The pipe identity is non-empty, 1..64 printable ASCII characters, and must match exactly. At display time, the helper independently captures an immutable expected binding and first proves that it equals the binding derived from authenticated evidence, the validated request, the authoritative digest, and the connected pipe. At Apply time it independently captures the actual binding. Apply uses its distinct helper-owned timestamp and atomically changes the lease from `Available` to `Consumed` before journal preparation only when all nine actual components exactly equal the display-time binding. Cancel, close, timeout, second or concurrent Apply, any changed binding component, a different helper instance, or replay refuses. The lease is not persisted and cannot survive a crash or process restart.

## Terminal state machine

```text
Created -> Listening -> HelperLaunched -> MutuallyAuthenticated
        -> RequestAccepted -> Reobserved -> AwaitingHelperApply
        -> ConsentConsumed -> JournalPrepared -> Executing -> Verified
        -> TerminalWritten -> Closed
```

Every internal outcome maps deterministically to exactly one externally visible specification result: `completed`, `canceled`, `repairNeeded`, `refused`, or `unknown`; then the single terminal-emission gate atomically attempts one terminal write and closes. A confirmed write exposes its mapped terminal. An unconfirmed or lost write exposes dashboard `unknown` with no delivered helper terminal, regardless of the candidate result. Before `ConsentConsumed`, zero mutation is possible. A crash before `JournalPrepared` maps to unconfirmed `unknown`, leaves no mutation, and cannot recover consent after restart. A crash after journal preparation maps to `repairNeeded` only if its terminal is confirmed; otherwise the dashboard remains `unknown` until separately authorized reconciliation. The dashboard never retries automatically and never turns pipe closure into success.

## Unsigned development guard and production gate

There is no unsigned fallback in production policy. Production peer authorization always requires the administrator-protected installed path, manifest version/hash, `WinVerifyTrust`, and pinned trusted signer. A helper in a repository, build, temporary, user-writable, or downloaded directory is never production-ready. This remains deliberately unavailable until v0.8 defines packaging, installation ACLs, signing, and update trust.

An unsigned helper may exist only in a separately built disposable-VM prototype harness. Its in-memory test policy requires all of: an explicit disposable-VM marker, a known-restorable snapshot identifier, and a non-empty unique namespace beginning `BallsServer.Test.`. The harness exposes no production composition entry point and no mutation adapter. Missing any guard refuses. The v0.3 developer-host feasibility probe does not invoke this escape: it uses only a same-user ephemeral pipe and process-ID APIs, then deterministically closes both processes and handles.

The owner subsequently accepted the narrowly scoped unsigned v0.4 pilot exception in [ADR 0006](../adr/0006-allow-explicit-unsigned-v0.4-pilot-helper.md). That decision does not revise the v0.3 evidence or the signed production gate; it permits only the explicit public pilot flow and keeps the signed, administrator-protected helper as the official-release requirement.

## Prototype evidence and limits

The isolated projects under `.scratch/v0.3.0/prototypes/privileged-helper-boundary*` model strict requests/results, peer evidence, re-observation digest comparison, replay, consent lifetime/consumption, terminal/secret cardinality, redaction, crash states, and the unsigned test guard. The live feasibility test creates a `CurrentUserOnly` ephemeral named-pipe server before a child client, proves both kernel-reported process IDs, performs one bounded exchange, and cleans up. It does not elevate, show UI, install or sign files, use the production DACL, or mutate Windows state.

The prototype is intentionally absent from `BallsServer.slnx`, `src/`, production composition, and the default 210-test suite. It creates no account, group, ACE, share, firewall rule, service, scheduler, listener, credential, mapping, policy, file in the managed folder, or durable machine state.
